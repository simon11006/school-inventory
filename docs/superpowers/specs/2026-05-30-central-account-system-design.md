# 중앙 계정 시스템(학교 계정·승인·짧은 주소) 설계서

> 작성일: 2026-05-30
> 상태: 설계 검토 대기 (구현 전 사용자 승인 필요)

## 1. 목표 (한 줄)

각 학교 담당자가 **구글 계정이 아니라 사이트 발급 아이디/비밀번호**로 로그인하고, 총괄관리자가 가입을 승인하며, 인계가 와도 **같은 학교 아이디**를 계속 쓰도록 만든다. 동시에 학교의 실제 데이터(물품·예약·교사 명부)는 지금처럼 **각 학교 자기 구글 스프레드시트에만** 남긴다.

## 2. 배경과 핵심 제약

현재 구조:
- 학교마다 자기 구글 스프레드시트 + Apps Script 웹앱을 소유한다.
- 연결은 딥링크 `?d=<배포ID>&k=<연결키>` 로 자동 설정된다.
- 중앙 서버가 없다. 인계가 번거롭다(구글 계정 소유권이 핵심 걸림돌).

이번 기능에서 **바뀌지 않는 것**:
- 학교의 실제 재고 데이터(물품/예약/로그/교사/위치/설정)는 **여전히 각 학교 구글 시트에만** 저장된다. 개발자/중앙 시스템은 재고 데이터에 접근하지 않는다.
- 웹앱이 학교 구글 계정 권한으로 동작한다는 근본 제약은 그대로다. (그 구글 계정이 사라지면 그 학교 웹앱도 사라진다 — 중앙 계정이 이걸 대신 막아주지는 못한다.)

이번 기능에서 **새로 생기는 것**:
- 중앙에 **학교 명부(계정 + 연락 이메일 + 연결 포인터 + 활용 상태)** 를 둔다.
- 가입/승인 절차가 생긴다.
- 짧은 접속 주소(`/s/짧은코드`)가 생긴다.
- 총괄관리자가 활용 학교/미활용 학교를 한눈에 본다.

## 3. 아키텍처

**백엔드: Firebase (Authentication + Firestore)** — 사용자 확정.

```
[학교 담당자 브라우저]
      │  아이디/비번 로그인
      ▼
[Firebase Authentication]  ← 로그인 인증만 담당
      │
      ▼
[Firestore: schools 컬렉션]  ← 학교 명부(연락처·승인상태·연결 포인터·활용상태)
      │
      │  연결 포인터(배포ID + 연결키) 조회
      ▼
[각 학교 Google Apps Script 웹앱] ── [각 학교 Google 스프레드시트]  ← 실제 재고 데이터(중앙 저장 안 함)
```

설계 결정과 그 보안적 의미:
- **재고 데이터는 중앙에 절대 저장하지 않는다.** Firestore에는 데이터로 들어가는 "열쇠"(배포ID + 연결키)와 연락/상태 정보만 둔다.
- **연결 포인터(배포ID + 연결키)는 Firestore에 저장한다.** 짧은 주소(`/s/코드` → 연결정보 조회 → 자동 연결)를 구현하려면 코드로 연결정보를 찾을 수 있어야 하기 때문이다. 이는 현재 긴 딥링크가 이미 연결키를 URL에 담아 공유하던 것과 **보안 수준이 동일**하다(접근 권한 부여 방식은 그대로, URL만 짧아짐).

## 4. 사용자 역할 정리

세 종류의 사람이 있고, 헷갈리기 쉬우니 명확히 구분한다.

| 역할 | 로그인? | 무엇을 하나 |
|---|---|---|
| **총괄관리자**(사이트 운영자=개발자) | 예(별도 권한) | 가입 승인/거부, 전체 학교 현황(활용/미활용) 확인 |
| **학교 담당자**(관리자) | 예(사이트 발급 학교 아이디) | 학교 가입, 연결정보 등록, 짧은 링크 발급, 인계 |
| **학교 교사**(일반 사용자) | 아니오 | 짧은 링크로 접속해 평소처럼 사용(가입·로그인 불필요) |

용어 충돌 주의: 앱 안에는 이미 **관리자 PIN(기본 1234)** 이 있다. 이건 "앱 내부 관리 기능" 잠금이다. 이번에 추가하는 **학교 로그인**은 "중앙 계정(가입·연결·인계 관리)" 용이다. 두 개는 서로 다른 층이며 그대로 공존한다.

## 5. Firestore 데이터 모델

`schools/{docId}` 문서:

```
{
  schoolName:  "서울초등학교",        // 가입 단위(실명 아님, 학교 이름)
  username:    "seoul-elem-01",       // 로그인 아이디(사이트 발급/선택)
  email:       "admin@xxx.sen.go.kr", // 연락용(필수, 동의받음) — 기관 이메일 권장
  contactName: "",                    // 담당자 이름(선택)
  status:      "pending",             // pending | approved | rejected | suspended
  shortCode:   "a3f9",                // 짧은 주소용 코드(승인 시 발급)
  connection: {                       // 학교 데이터 연결 포인터(재고 데이터 아님)
    deploymentId: "",                 // ?d= 값
    apiKey:       "",                 // ?k= 값
    webAppUrl:    ""                  // /exec 주소(배포ID 추출 실패 시 fallback)
  },
  lastActiveAt: <timestamp>,          // 활용 추적(heartbeat)
  createdAt:    <timestamp>,
  approvedAt:   <timestamp|null>,
  consentAt:    <timestamp>           // 개인정보 동의 시각
}
```

- Firebase Auth는 로그인 아이디를 이메일 형식으로 요구한다. 로그인용으로는 `username@item-school.app` 같은 **비라우팅 내부 이메일**을 합성해 쓰고, **연락용 진짜 이메일은 Firestore `email` 필드에 따로 저장**한다. 즉 로그인은 학교 아이디로, 연락은 진짜 이메일로 분리한다.
- `shortCode` 는 충돌 없는 짧은 코드(4~6자)로 발급한다.

## 6. 화면·흐름

### 6-1. 가입 화면
입력: 학교 이름, 로그인 아이디, 비밀번호, 연락 이메일(필수), 담당자 이름(선택).
필수: **개인정보 동의 체크박스**(목적: 장애/공지 연락, 수집항목: 이메일·(선택)담당자명, 보유기간 명시). 동의 안 하면 가입 불가.
결과: Firebase Auth 사용자 생성(비밀번호 설정) + Firestore 문서 `status:"pending"` 생성. 화면에는 "승인 대기 중" 안내.

### 6-2. 로그인 화면
아이디 + 비밀번호 → Firebase Auth 인증 → Firestore `status` 확인:
- `pending` → "승인 대기 중입니다" 안내, 진행 차단
- `approved` → 학교 작업 화면 진입
- `rejected`/`suspended` → 사유 안내, 진행 차단

### 6-3. 연결 설정(로그인 후)
승인된 담당자가: 스프레드시트 사본 만들기 → 웹앱 배포 → 연결정보(배포ID/연결키 또는 `/exec` URL) 입력/붙여넣기. Firestore `connection` 에 저장. (기존 `?d=&k=` 딥링크 캡처 흐름을 재사용해 자동 채움도 가능.)

### 6-4. 짧은 주소 발급/조회
- 발급: 승인 시 `shortCode` 생성. 담당자 화면에 `https://item-school.app/s/a3f9` 표시(학교 내부 메신저로만 공유 안내 유지).
- 조회: 교사가 `/s/a3f9` 접속 → Firestore에서 `shortCode→connection` 조회 → 기존 `applySyncFromUrl` 과 동일하게 자동 연결 → 평소처럼 사용.

### 6-5. 활용 추적(heartbeat)
학교 데이터 load/save 성공 시 해당 학교 `lastActiveAt` 갱신. 총괄관리자 대시보드에서 **최근 활동(활용) vs 오래 멈춤(미활용)** 구분.

### 6-6. 총괄관리자 대시보드
- 가입 신청 목록(승인/거부)
- 전체 학교 목록: 학교명, 상태, 마지막 활동일, 연락 이메일, (선택)담당자명, 활용/미활용 배지, 정지(suspend) 기능.

## 7. 인계가 실제로 좋아지는 점(그리고 한계)

좋아지는 점:
- 학교 **정체성과 연결정보가 중앙에 남는다.** 후임이 **같은 학교 아이디**로 로그인하면 연결정보·짧은 링크를 그대로 본다.
- 후임이 새 배포를 했을 때 **연결정보만 갱신**하면 짧은 링크는 그대로 유지된다(교사에게 새 링크 재배포 불필요).
- 총괄관리자가 "이 학교 아직 쓰고 있나?"를 활용 추적으로 확인 가능.

여전한 한계(정직하게 명시):
- 구글 스프레드시트/웹앱은 **여전히 어떤 구글 계정 소유**다. 그 계정이 사라지면 그 학교 데이터/웹앱은 사라진다. 중앙 계정은 이걸 못 막는다. 따라서 **소유권 이전(또는 학교 공용 구글 계정 사용)** 안내는 그대로 필요하다.

## 8. 보안·개인정보

- 이메일은 개인정보보호법상 개인정보 → **동의 체크박스 + 목적/보유기간 고지** 필수. **학교 담당자만 동의**(교사는 가입하지 않으므로 무관). 기관 이메일 권장. (법률 자문 아님.)
- Firestore 보안 규칙: 학교 문서는 본인(해당 학교 계정)만 자기 문서 읽기/쓰기, 총괄관리자만 전체 읽기/상태 변경, `shortCode→connection` 조회는 공개 읽기(교사 무로그인 접속 위해) 또는 제한된 콜러블 함수로 노출.
- 연결키(API key)+웹앱 URL = 학교 데이터 접근 열쇠. "학교 내부 메신저로만 공유" 안내 유지. 외부 SNS·메일·홈페이지 공개 금지.
- 관리자 PIN 기본값 1234 변경 안내 유지.
- `① 처음 설정`(전체 시트 초기화)은 인계 중 절대 실행 금지 안내 유지.

## 9. 기존 사용자와의 공존

- 기존 `?d=&k=` 딥링크로 쓰던 학교는 **그대로 동작**한다(중앙 계정은 추가 레이어, 강제 아님).
- 신규 학교는 가입 흐름을 탄다. 기존 학교는 원하면 나중에 계정 등록으로 합류.

## 10. 단계별 진행 계획(개요)

| 단계 | 내용 | 산출물 |
|---|---|---|
| 1 | Firebase 프로젝트·Auth·Firestore·보안규칙 셋업 | firebase 설정, 빈 `schools` 컬렉션 |
| 2 | 가입 화면 + 개인정보 동의 | 가입 → pending 문서 생성 |
| 3 | 로그인 + 상태 게이팅 | approved만 진입 |
| 4 | 총괄관리자 승인 대시보드 | 승인/거부, shortCode 발급 |
| 5 | 연결정보 저장 + 짧은 주소 조회 | `/s/코드` 자동 연결 |
| 6 | 활용 추적(heartbeat) + 활용/미활용 표시 | 대시보드 배지 |
| 7 | 기존 인계 흐름과 통합 | 인계 점검 화면에서 계정/연결 갱신 안내 |

## 11. 검토 필요 항목(사용자 확인용)

1. 로그인 아이디를 **사이트가 발급**(예: `학교코드-번호`)할지, **담당자가 직접 정할지**.
2. 짧은 주소 형식: `item-school.app/s/a3f9` 형태로 OK인지(현재 Netlify 도메인 `item-school.netlify.app` 기준이면 `/s/` 라우팅 추가 필요).
3. 총괄관리자(개발자) 인증 방식: 별도 Firebase 계정 1개로 운영할지.
4. 미활용 기준: 마지막 활동 후 며칠(예: 30일/60일)부터 "미활용"으로 볼지.
